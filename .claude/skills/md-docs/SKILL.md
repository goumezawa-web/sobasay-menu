# Markdownドキュメント規約

## 共通ルール

- **秘密情報の実値(APIキー・シークレット・トークン)は絶対に書かない**。保管場所と管理者だけを書く(台帳方式)
- 未確定の値は **【 】** プレースホルダーにし、文末に「記入前チェックリスト」を付ける
- 冒頭に `最終更新: YYYY-MM-DD / 状態: ○○`、文末に `## 更新履歴` を置く
- ファイル名は `NN_内容.md`(連番で並び順を固定)。日本語ファイル名可
- 図はASCIIで描く(NASなどレンダラの無い環境でも読めるように)。表は短い列挙のみ、説明は本文で
- 納品: 単発ファイルはSendUserFile、複数はフォルダごとzip。**NASの原本とリポジトリ管理のどちらが正か**を文書内に明記

## 種類別テンプレート

### 1. 指示書(AI実行用スペック) — COSA式

「スマホを渡して30秒で伝わる」等、**成果物の使われ方**から書き始める。

```
# ○○ 開発指示書(Claude Code用)
## 0. ゴールとスコープ    ← 何のため・誰に見せる・完成度の優先順位
   Phase A(今回)/ Phase B(今回は作らない。ただし設計だけ意識)
## 1. 技術スタック        ← 差し替え前提の箇所は「分離しておく」と明記
## 2〜N. 機能仕様         ← 番号付き。数値は具体的に(+10pt、7日で減衰 等)
## デザイントーン          ← 客層と「幼稚にしない」等の境界条件
## 受け入れ基準            ← - [ ] 形式。機械的に判定できる文のみ
## やらないこと(明記)      ← スコープ外を先に潰す
```

コツ: 完成条件が書けない依頼は「完成条件を相談する」タスクとして先に出す。
デモ用シードデータ(毎回ゼロから始めない)とリセット手段を仕様に含める。

### 2. 手順書(本人・スタッフの操作手順)

```
# ○○の手順
目的(1行) / 所要時間 / 前提(必要なもの・権限)
## 手順               ← 番号付き。1ステップ=1操作。ボタン名・メニュー名は「」で正確に
## つまずきポイント    ← 実際に起きたエラーと対処だけを書く(想像で書かない)
## 完了確認           ← 「○○が表示されれば完了」と判定可能に
```

### 3. 事業ドキュメント(NAS保管・AI事業部共有)

```
# NN 事業名
最終更新: YYYY-MM-DD / 状態: ○○
## 1. 目的
## 2. 現状(基本情報の表)
## 3. 構成
## 4. 連携          ← 表: 連携元 | 連携先 | 方式 | 認証(値の置き場所) | 状態
## 5. 認証情報の扱い ← 実値は書かず保管場所と管理者のみ
## 6. 運用手順
## 7. 残タスク       ← - [ ] 形式
## 8. 更新履歴
```

複数事業をまとめるときは `00_全体マッピング.md`(連携図+認証情報台帳+権限境界+URL一覧)と `README.md`(読み方)を先頭に置く。
