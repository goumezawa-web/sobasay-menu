# Opusを最大限引き出す依頼の書き方

Claude Code(Opus)への依頼文のガイド。Opusは「最初に全体像を渡して任せる」ほど性能もトークン効率も上がり、小出しの追加指示はどちらも下げる。

## 依頼テンプレート

```
【目的】なぜやるか・誰のためか(1〜2行)
【やること】具体的な作業内容
【完成条件】できた/できてないを機械的に判定できる条件(箇条書き)
【制約】触ってはいけない箇所、守るべき規約、期限など
【任せる範囲】細部の判断は任せる/ここだけは確認してほしい、の線引き
```

タスク台帳(tasks.json)の why / done_condition と同じ発想。依頼の時点で完成条件を書けないタスクは、先に完成条件を相談するタスクとして出す。

### 例

> 【目的】ポスター取込の生成品質を上げたい(顧客デモ用)
> 【やること】poster/index.html のプロンプトを改善し、縦書きテキストの復元に対応
> 【完成条件】縦書きポスター画像でテキストが writing-mode: vertical-rl で復元される / 既存のE2Eテストが全部通る
> 【制約】ガワ合成の分担(SHELL_*)は崩さない。トークン消費を増やさない
> 【任せる範囲】実装方法は任せる。プロンプト文面の最終版だけ報告して

## 効くコツ

1. **1ターンで全部渡す** — 背景・完成条件・制約を最初に。後出しの追加指示はやり直しコストとトークンの両方を増やす
2. **「調べて直して」より「〜という症状。原因を調べて報告」** — 調査と修正を分けると、意図しない修正を防げる(検品もしやすい)
3. **完成条件は検証可能に** — 「いい感じに」ではなく「B5原寸で印刷したとき文字が切れない」
4. **難しい問題ほどOpus向き** — 単純作業の指示を細かく書くより、難題を丸ごと渡して自己検証までさせる方が真価が出る
5. **並列を明示的に許可** — 「独立な部分はサブエージェントで並列に進めてよい」と書くと長い作業が速くなる

## トークンと性能のダイヤル

| 場面 | 設定 |
|---|---|
| 通常の開発作業 | opus + effort high(このリポジトリの既定) |
| 最難関の設計・デバッグ | セッション内で effort を xhigh に上げる |
| 単純な一括置換・確認 | `/model haiku` で十分(約1/5のコスト) |
| 使い分けの原則 | モデルを下げるより「依頼を明確にする」方が節約効果が大きい |
